# TODO Audit — Backend, UI, dan Alur Penilaian (25 September 2026)

Sesi kerja baru untuk Gemini. Sumber kebenaran tetap [PRD](docs/PRD.md), [ERD](docs/ERD.md), [AI Rules](docs/AI_RULES.md), dan [AGENTS.md](AGENTS.md); dokumen ini bukan pengganti [TODO.md](TODO.md) fase F0–F8, melainkan daftar temuan audit Claude Code yang berdiri sendiri dan siap dikerjakan terpisah.

Cakupan audit: kode backend (`app/`, migrations), UI (`resources/js`, `resources/css`), dan alur fitur penilaian end-to-end (CAP-04/05/06), dibandingkan terhadap kontrak PRD/ERD/AI_RULES yang berlaku. Tidak ditemukan blocker; seluruh item di bawah adalah gap konkret dengan lokasi file:baris dan instruksi perbaikan.

Aturan pengerjaan:
- Kerjakan sesuai urutan prioritas (tinggi lebih dulu), boleh diselingi bila ada dependensi teknis.
- Setiap item ditutup (`[x]`) hanya setelah pemeriksaan terkait benar-benar dijalankan; catat command dan hasilnya di bagian **Verifikasi** di bawah, bukan sekadar mengubah kode.
- Jangan mengubah kontrak skor CAP-04, ownership, atau immutability versi saat memperbaiki item ini kecuali item itu sendiri memang tentang itu.
- Jika suatu item ternyata sudah tidak relevan (mis. kode sudah berubah sejak audit), jelaskan alasannya di catatan verifikasi alih-alih menghapus baris diam-diam.

## Alur fitur penilaian (CAP-04/05/06 end-to-end)

- [x] 13. **[Medium]** `resources/js/Pages/Assessments/Index.tsx:55` — Tampilkan link "Lihat hasil" berdasarkan `record.current_final_id` (bukan bergantung `record.draft_id`); sembunyikan hanya "Koreksi"/"Batalkan hasil" saat draft revisi sedang berjalan. Hasil final lama harus tetap terlihat selama revisi berlangsung (AI_RULES: current final tetap tampil sampai revisi sukses).
- [x] 14. **[Medium-High]** `app/Http/Controllers/AssessmentController.php:35` (`work()`) — Ganti pemanggilan `$drafts->show()` yang hasilnya dibuang (hanya dipakai efek samping ownership check) dengan pemeriksaan keberadaan/ownership ringan, agar payload detail lengkap (edisi, rubrik, ranges, ayat+kata) hanya dihitung sekali oleh frontend. Saat ini setiap buka sesi menjalankan query berat dua kali, berisiko terhadap budget PRD "buka sesi p95 ≤2 detik" pada skala 10.000 sesi.
- [x] 15. **[Medium]** `app/Services/AssessmentDrafts.php` (`validateEvents`) dan `resources/js/Pages/Assessments/Work.tsx` (blok catch pada `save()`) — Saat actual range diperkecil membuat anotasi aktif keluar cakupan, sertakan identitas event/anotasi bermasalah pada respons 422 (bukan hanya pesan error generik), dan tampilkan di frontend affordance "pindahkan/batalkan anotasi ini" tepat di anotasi tersebut, sesuai maksud CAP-06.

## Alur penilaian — evaluasi lanjutan (27 September 2026)

Audit ulang atas permintaan pemilik proyek, fokus khusus pada alur sesi penilaian (CAP-04/05/06) setelah 15 item di atas selesai. Belum dikerjakan — direncanakan untuk sesi berikutnya. Kalkulasi skor (CAP-04) sendiri sudah sesuai kontrak dan lolos test; temuan di bawah semuanya soal alur kerja seputar sesi, bukan rumus skor.

- [ ] 16. **[High]** `resources/js/Pages/Assessments/Work.tsx` (tidak ada `setInterval`/debounce, tidak ada `beforeunload`) — Implementasikan autosave draft sesuai CAP-06 ("Autosave draft"). Saat ini simpan hanya lewat tombol manual "Simpan Draf" (`Work.tsx:958`); jika guru menandai banyak anotasi lalu tab tertutup/refresh/koneksi putus sebelum klik simpan, semua perubahan hilang tanpa peringatan. Tentukan interval autosave dan tambahkan guard `beforeunload` saat `state === 'unsaved'`.
- [ ] 17. **[High]** `app/Services/AssessmentDrafts.php:196` (`save()`, pesan "Bacaan aktual harus berada dalam materi rencana") dan `resources/js/Pages/Assessments/Work.tsx` — Tidak ada route/tombol untuk memperluas `planned_ranges` setelah draft dibuat, padahal CAP-06 mensyaratkan "perluas planned secara eksplisit jika bacaan bertambah". Saat ini bila santri membaca lebih dari rencana, satu-satunya jalan guru adalah membatalkan draft dan kehilangan semua anotasi yang sudah dibuat. Tambahkan endpoint + UI untuk memperluas planned ranges pada draft yang masih berjalan.
- [ ] 18. **[Medium]** `resources/js/Pages/Assessments/Work.tsx:140-150` (`toggleWordPenalty`) dan `resources/js/Pages/Assessments/Work.tsx:513-522` (handler klik token akhir ayat) — Pencarian "anotasi aktif apa pun" pada kata/ayat tidak memfilter berdasarkan rule, sehingga begitu ada satu penalti aktif, klik berikutnya selalu meng-undo penalti itu bukan menambah penalti kedua dari kriteria lain. Ini melanggar CAP-04: "Satu kejadian penalti memotong satu kriteria. Jika guru memang ingin dua dampak, buat dua kejadian eksplisit." Backend sudah mendukung banyak event per anchor; perbaikan hanya perlu di logika toggle frontend (filter existingActive berdasarkan `rule_id` yang sama dengan `selectedRule`, bukan berdasarkan anchor saja).
- [ ] 19. **[Medium]** `resources/js/Pages/Assessments/Work.tsx:744-774` (panel "Hasil & Skor Sesi") — Tidak ada indikator per-kriteria yang menjelaskan kriteria mana yang gagal ambang (`min_pass_normalized`). Contoh wajib PRD CAP-04 ("ambang tajwid 85 → tidak lulus walau nilai akhir 86") menunjukkan kegagalan bisa berasal dari ambang kriteria, bukan cuma ambang akhir, tapi guru hanya melihat status "Lulus/Belum Lulus" agregat tanpa tahu kriteria mana penyebabnya. Perlu backend mengirim status pass/fail per kriteria (bandingkan `normalized` terhadap `min_pass_normalized`) dan frontend menampilkannya di baris kriteria terkait.
- [ ] 20. **[Low-Medium]** `resources/js/Pages/Assessments/Work.tsx:744-774` dan `app/Services/ScoreCalculator.php` (`display_score`) — PRD CAP-04 contoh wajib: "Nilai 79,999 dengan ambang 80 → tidak lulus; UI menjelaskan pembulatan walau tampilan 80,00." Saat ini tidak ada penjelasan kontekstual saat `display_score` yang dibulatkan (mis. "80.00") berbeda dari keputusan lulus/tidak yang dihitung dari nilai belum dibulatkan — bisa membingungkan guru/santri. Tambahkan teks penjelasan singkat di panel skor saat kasus ini terjadi (nilai tampilan di ambang tapi status tidak lulus/lulus karena nilai sebenarnya sebelum pembulatan).
